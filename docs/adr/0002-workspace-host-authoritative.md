# 工作区采用房主权威，不做多写者合并

2026-10-27 第二轮裁决：工作区（挂在项目下的共享项目空间）采用**房主权威模型**——房主设备是唯一真源，成员签名提交事件、房主定序并广播，各端只做缓存与投影；同一协议预留中心服务宿主位（P2P + 中心双宿主，中心为后续可选项）。否决两个替代：多写者签名事件日志（无主机、确定性合并——用合并与冲突语义换"房主离线仍可写"，不值）与 CRDT / automerge-repo（解决高频并发文本编辑，本场景低频结构化写零收益且事件可读性差）。理由：与 Multica / Huly 的中心权威同构（宿主从服务器换成房主设备），实现面最小、序天然全序、审计清晰；代价（房主离线即只读）已被明确接受。同轮裁定：session 镜像只读 + 显式 attach（不自动圈定、不落库，驾驶延后）；CC 是工作区与信箱的唯一自动联动。

## Considered Options

- 多写者事件日志 + 确定性合并 —— 拒：可用性收益抵不上合并语义复杂度。
- CRDT（automerge-repo 自定义网络适配）—— 拒：依赖重、事件流人不可读。
- 中心服务宿主先行 —— 延后：v1 无部署形态；协议按双宿主设计，跨网诉求出现时先做中心宿主再评估 iroh。

## Consequences

- 房主设备是可用性单点（合盖 = 全员只读）；缓解：常开机器、后续所有权转让。
- 事件序由房主分配；跨宿主迁移（→ 中心服务）需要序延续策略，届时另立 ADR。
- 各端缓存投影离线可读，写路径快速失败；信件路径与工作区路径互不依赖。
